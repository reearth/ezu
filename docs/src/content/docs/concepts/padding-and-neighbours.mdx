Filters read pixels around the pixel they write. Near a tile edge those pixels
are outside the tile. Two mechanisms deal with that: a padded canvas for
raster-space filters, and neighbour tiles for data that has to be genuinely
continuous.

## The padded canvas

A style declares `pad`, and rendering happens on a canvas of
`tile-size + 2 × pad` on each axis, with real geometry drawn into the margin. The
margin is cropped off at the end.

```json
{ "name": "mine", "tile-size": 512, "pad": 24, "…": "…" }
```

Every `Raster` and `ScalarField` in the graph is this padded size, which is why
those kinds are described as "padded canvas-sized".

## Padding is computed, not guessed

You do not have to work out how much margin a chain needs. Each node declares how
it grows the requirement — `blur` asks for `3σ`, and so on — and
`Graph::compute_pad` walks the topological order in reverse to arrive at what each
source must supply.

If the result exceeds the maximum, the build fails. A `blur` with `sigma: 200`
wants ~600 px of margin on every side; being told that at build time is better
than discovering it in a memory profile.

## Why static bounds are required

Padding must be known before evaluation, so a field that determines it must have
a build-time upper bound:

```json
"sigma": 3                              // ✅ literal
"sigma": "$softness"                    // ✅ if the param declares `max`
"sigma": "@computed"                    // ❌ build error — a port has no static bound
```

This is the one place where the otherwise-uniform `In<T>` flexibility is
restricted, and the error message says so explicitly.

## Setting `pad` in practice

- **Plain vector recipes** — 8–16 px covers wide strokes and label halos.
  `ezu translate` emits 16.
- **Painterly styles** — 24 px and up. Dab radius, warp amplitude, and blur sigma
  all eat margin.
- **Too small** shows as darkened or clipped edges. **Too large** costs render
  time on pixels you throw away — the canvas grows quadratically, so 512+2×64 is
  1.6× the pixels of 512+2×16.

Start from what the filters need and only raise it if edges look wrong.

## Neighbour tiles

Padding solves raster-space filters, because the geometry needed for the margin
is fetched with the tile. Two things need more than that:

- **DEM and raster imagery.** A hillshade computed from a single DEM tile steps
  at the border, because the gradient at the edge needs the neighbour's
  elevations. The host stitches the 3×3 neighbourhood into one per-tile field
  before evaluation.
- **Label collision.** Candidates from the eight neighbouring tiles participate
  in placement, so both sides of a border agree — see
  [tiles and determinism](/ezu/concepts/tiles-and-determinism/).

Nothing else reads neighbours. In a wasm host, ask rather than assume:

```js
r.requestedNeighborOffsets('terrain');   // [[dx, dy], …] — never [0, 0]; [] means centre is enough
```

That is nine fetches versus one, per source, so it is worth the call. Native
hosts get the same information through `requested_neighbor_offsets`.

## Missing neighbours

A neighbour that does not exist is normal at the edge of coverage. Raster and DEM
sources take an `on-missing` policy — `empty` (default), `upsample`, or `error` —
and requests past a source's `max-zoom` always upsample from the `max-zoom`
ancestor. See [sources and assets](/ezu/concepts/sources-and-assets/).
