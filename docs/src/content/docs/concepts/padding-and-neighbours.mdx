Filters read pixels around the pixel they write. Near a tile edge those pixels
are outside the tile. Two mechanisms deal with that: a padded canvas for
raster-space filters, and neighbour tiles for data that has to be genuinely
continuous.

## The padded canvas

A style declares `pad`, and rendering happens on a canvas of
`tile-size + 2 × pad` on each axis, with real geometry drawn into the margin. The
margin is cropped off at the end.

```json
{ "name": "mine", "tile-size": 512, "pad": 24, "…": "…" }
```

Every `Raster` and `ScalarField` in the graph is this padded size, which is why
those kinds are described as "padded canvas-sized".

## You do not have to compute it

Leave `pad` out and the renderer works it out. Each node declares how far it
reads past the pixel it writes — `blur` asks for `3σ`, `mosaic` for a block, a
`text` layer for the extent a label may cross a border by — and those distances
depend only on fields with a **static bound**, which is exactly why the answer is
knowable before anything renders:

```json
{
  "name": "soft",
  "tile-size": 512,
  "nodes": {
    "f":    { "op": "features", "layer": "earth" },
    "fill": { "op": "fill-solid", "features": "@f", "fill": "#c2410c" },
    "out":  { "op": "blur", "input": "@fill", "sigma": 12 }
  },
  "output": "@out"
}
```

```sh
ezu tile --style soft.json --tile 6/57/25 --out soft.png
# INFO pad: 0 declared, 36 needed — rendering with 36
```

When you *do* write `pad`, it is a **floor**, not the answer: the renderer takes
whichever is larger of your number and what the graph reaches. So a style asking
for a deliberately generous margin keeps it, and a style asking for too little
cannot silently end up with clamped edge pixels at the tile border.

:::note[It is a worst case]
A `$param` contributes its declared `max`. A blur whose sigma can reach 16 costs
48 px of margin on every render, including the ones that use `sigma: 0`. Two ways
to trade that back: declare a tighter `max`, or pin `pad` to a smaller number and
accept the edges you get. The canvas grows quadratically — 512+2×64 is 1.6× the
pixels of 512+2×16 — so it is worth a thought on a hot tile server, and worth
ignoring everywhere else.
:::

There is a ceiling, `MAX_PAD` at 256 px. A graph asking for more than that is
reported by `ezu check` and rendered with the style's own `pad` instead — a
`blur` with `sigma: 200` wants ~600 px of margin, which is a style bug rather
than a canvas size.

## Why static bounds are required

Padding must be known before evaluation, so a field that determines it must have
a build-time upper bound:

```json
"sigma": 3                              // ✅ literal
"sigma": "$softness"                    // ✅ if the param declares `max`
"sigma": "@computed"                    // ❌ build error — a port has no static bound
```

This is the one place where the otherwise-uniform `In<T>` flexibility is
restricted, and the error message says so explicitly.

## When to write `pad` anyway

- **You want a wider margin than the filters need.** Geometry that overflows the
  tile without any filter reading it — a wide stroke, a label halo — is drawn
  onto the margin too, and `pad` is how you make room for it. `ezu translate`
  emits 16 for exactly this.
- **You want a narrower one than the worst case.** A style whose blur sigma is a
  param with a generous `max` pays for that max on every tile; pinning `pad`
  trades edge quality at the border for pixels.

Otherwise leave it out. `ezu check` prints what the graph needs either way, so
you can see what you are choosing between.

## Neighbour tiles

Padding solves raster-space filters, because the geometry needed for the margin
is fetched with the tile. Two things need more than that:

- **DEM and raster imagery.** A hillshade computed from a single DEM tile steps
  at the border, because the gradient at the edge needs the neighbour's
  elevations. The host stitches the 3×3 neighbourhood into one per-tile field
  before evaluation.
- **Label collision.** Candidates from the eight neighbouring tiles participate
  in placement, so both sides of a border agree — see
  [tiles and determinism](/ezu/concepts/tiles-and-determinism/).

Nothing else reads neighbours. In a wasm host, ask rather than assume:

```js
r.requestedNeighborOffsets('terrain');   // [[dx, dy], …] — never [0, 0]; [] means centre is enough
```

That is nine fetches versus one, per source, so it is worth the call. Native
hosts get the same information through `requested_neighbor_offsets`.

## Missing neighbours

A neighbour that does not exist is normal at the edge of coverage. Raster and DEM
sources take an `on-missing` policy — `empty` (default), `upsample`, or `error` —
and requests past a source's `max-zoom` always upsample from the `max-zoom`
ancestor. See [sources and assets](/ezu/concepts/sources-and-assets/).
